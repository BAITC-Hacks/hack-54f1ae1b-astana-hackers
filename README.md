# WindPower Agent

ML-базовая система прогнозирования почасовой выработки ветроэлектростанции

## 1. Название проекта

**WindPower Agent** — baseline-версия решения для прогноза нормализованной активной мощности двух ветряных турбин.

## 2. Краткое описание

Проект решает задачу краткосрочного прогнозирования выработки ВЭС на горизонте 24–48 часов. Решение преобразует исторические 10-минутные измерения в почасовой ряд, строит прогноз по зависимости «скорость ветра → мощность» и сравнивает её с ML-моделью на основе погодных признаков и истории выработки.

Решение предназначено для:

- участников и жюри хакатона, которым нужна воспроизводимая проверка качества модели;
- операторов ВЭС и диспетчеров, которым нужен ориентир по ожидаемой мощности;
- дальнейшего расширения до agentic AI-системы с погодным агентом и регулярным пересчётом прогноза.

Текущая версия прогнозирует **нормализованную активную мощность** от 0 до 1. Для перевода в кВт или МВт потребуется установленная мощность турбины.

## 3. Что реализовано

- чтение CSV двух турбин;
- нормализация названий и типов колонок;
- обработка дубликатов временных меток;
- агрегация 10-минутных измерений в почасовую сетку;
- контроль полноты часа через число исходных измерений;
- baseline-модель `PowerCurveRegressor` с биннингом скорости ветра по 1 м/с;
- `RidgePowerRegressor` на признаках ветра, температуры, календаря, лагов и rolling-статистик;
- рекурсивный прогноз на 24 и 48 часов;
- walk-forward-валидация по дневным точкам прогноза;
- расчёт MAE, RMSE и WMAPE;
- сохранение результатов в JSON.

## 4. Как работает решение

Основной сценарий запуска:

1. Пользователь передаёт пути к CSV двух турбин.
2. Скрипт читает исходные данные и приводит колонки к единому формату.
3. 10-минутные записи агрегируются по часам: ветер, температура и мощность усредняются.
4. Неполные часы исключаются из обучения и проверки, а пропуски не подменяются фактическим target.
5. Обучаются две модели: power curve и ridge-регрессия.
6. Модели проверяются на исторических дневных точках с горизонтами 24 и 48 часов.
7. Метрики и результаты по каждому запуску записываются в `outputs/ml_benchmark.json`.

В production-сценарии текущие погодные колонки должны поступать от weather API как прогноз, доступный на момент формирования прогноза. В benchmark-версии для исторической проверки используются фактически измеренные ветер и температура, поэтому эта проверка является weather-aware benchmark, а не полной симуляцией архивного прогноза погоды.

## 5. Технологии

- **Python 3.10+**;
- **pandas** — чтение CSV, временные ряды и агрегация;
- **NumPy** — расчёт признаков и ridge-регрессии;
- **Python standard library** (`urllib`, `json`, `csv`, `hashlib`, `zoneinfo`) — загрузка и versioning архивных weather runs;
- **JSON** — сохранение метрик;
- **argparse** — интерфейс командной строки;
- **Git/GitHub** — версионирование проекта.

Используемые модели:

- `PowerCurveRegressor` — физически интерпретируемый baseline;
- `RidgePowerRegressor` — регуляризованная линейная модель с нелинейными признаками скорости ветра.

В текущей версии не используются LightGBM, XGBoost, PyTorch или LLM API.

Для архивных погодных прогнозов добавлен `weather_archive.py`, который использует Open-Meteo Single Runs API. LLM API не требуется.

## 6. Архитектура проекта

```text
datasets/*.csv
       │
       ▼
ml_baseline.py
       │
       ├── read_turbine_csv()
       ├── to_hourly()
       ├── make_features()
       │
       ├── PowerCurveRegressor
       ├── RidgePowerRegressor
       │
       ├── recursive_forecast()
       └── evaluate_origins()
                │
                ▼
outputs/ml_benchmark.json
weather_archive.py
       │
       ▼
outputs/weather_archive/manifest.jsonl + runs/*/response.json + runs/*/forecast.csv
```

Главная логика находится в одном файле `ml_baseline.py`. Функции чтения и подготовки данных отделены от моделей, а функция оценки запускает одинаковую walk-forward-проверку для обеих моделей.

## 7. Установка и запуск

Откройте PowerShell и перейдите в корень репозитория:

```powershell
cd "C:\Users\user\Desktop\hackaton\hack-54f1ae1b-astana-hackers"
```

Установите зависимости:

```powershell
python -m pip install --upgrade pip
python -m pip install pandas numpy
```

Если используется конкретный интерпретатор Windows:

```powershell
& "C:\Python312\python.exe" -m pip install pandas numpy
```

Запустите benchmark:

```powershell
& "C:\Python312\python.exe" ".\ml_baseline.py" `
  --turbine1 ".\datasets\Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv" `
  --turbine2 ".\datasets\Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 2.csv" `
  --output ".\outputs\ml_benchmark.json"
```

Загрузить и сохранить архивный прогноз на 48 часов для запуска 31 января 2026 года:

```powershell
& "C:\Python312\python.exe" ".\weather_archive.py" `
  --as-of "2026-01-31T00:00" `
  --horizon-hours 48 `
  --output-dir ".\outputs\weather_archive"
```

Для проверки без сетевого запроса используйте `--dry-run`. Команда покажет выбранный UTC run и URL для каждой турбины:

```powershell
& "C:\Python312\python.exe" ".\weather_archive.py" `
  --as-of "2026-01-31T00:00" `
  --horizon-hours 48 `
  --dry-run
```

Параметр `--cutoff` задаёт начало периода walk-forward-валидации. Значение по умолчанию — `2026-01-04 00:00:00`.

## 8. Как проверить решение

Жюри может повторить следующий сценарий:

1. Клонировать репозиторий.
2. Установить `pandas` и `numpy`.
3. Убедиться, что два CSV находятся в `datasets/`.
4. Запустить команду из раздела выше.
5. Проверить вывод в консоли и файл `outputs/ml_benchmark.json`.

Посмотреть сохранённые метрики в PowerShell:

```powershell
Get-Content -Raw ".\outputs\ml_benchmark.json"
```

Для проверки синтаксиса без запуска benchmark:

```powershell
& "C:\Python312\python.exe" -m py_compile ".\ml_baseline.py"
```

Последний локальный benchmark на данных проекта:

| Турбина | Горизонт | Power curve MAE | Ridge MAE |
|---|---:|---:|---:|
| 1 | 24 ч | 0.0373 | 0.0386 |
| 1 | 48 ч | 0.0377 | 0.0388 |

На текущем validation-окне baseline power curve показывает меньшую MAE, поэтому он является рабочим ориентиром для следующего этапа развития модели.

## 9. Данные и интеграции

В репозитории используются два файла:

- `datasets/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv`;
- `datasets/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 2.csv`.

Исходные поля:

- идентификатор записи;
- статистическое время;
- средняя скорость ветра, м/с;
- нормализованная активная мощность;
- средняя температура окружающей среды, °C.

Координаты турбин передаются в Open-Meteo для выбора ближайшей наземной forecast grid cell.

`weather_archive.py` использует Open-Meteo Single Runs API и сохраняет:

- исходный JSON-ответ;
- нормализованный `forecast.csv`;
- `manifest.jsonl` с `as_of`, выбранным model run, координатами, URL, временем получения, размером горизонта и SHA-256 ответа.

Документация источника: <https://open-meteo.com/en/docs/single-runs-api>.

LLM-сервисы и deployed-инфраструктура в текущей версии отсутствуют.

## 10. Ограничения текущей версии

- нет agentic AI-цикла «получение погоды → подготовка → прогноз → анализ → повторный расчёт»;
- валидация использует фактические исторические ветер и температуру, а не архивные прогнозы, доступные в прошлом;
- нет отдельной модели LightGBM/XGBoost;
- нет quantile-прогнозов P10/P50/P90 и доверительных интервалов;
- нет полноценного ансамбля моделей;
- `weather_archive.py` уже получает архивные weather runs, но автоматическая подача сохранённого `forecast.csv` в ML-прогноз пока не объединена в одну команду;
- не рассчитывается абсолютная энергия в кВт·ч или МВт·ч, поскольку установленная мощность турбин не передана;
- нет веб-интерфейса, планировщика и мониторинга качества в production;
- рекурсивный прогноз ridge может накапливать ошибку на длинном горизонте.
